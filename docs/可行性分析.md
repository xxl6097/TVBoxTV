# 可行性分析：从 TVBox 生态到鸿蒙「夜帧影视」

> 结论先行：**不能转译，只能重写；重写后能覆盖 280 个站源里的 60 个。**
> 本文记录这个结论的完整证据，避免以后再走弯路。

## 一、两个上游仓库的真实性质

### 1. `zqc11608/box` —— 不是应用，是数据

克隆下来只有这些东西：

```
sub/   图片与子配置
vod/   点播相关片段
m.json     ← 65 KB，280 个 sites / 45 个 parses / lives / flags / ads
dm.txt     多仓配置
xiaopingguo.json
```

`m.json` 的顶层结构（实测解析）：

```json
{
  "sites":   [280],        // 站源定义
  "parses":  [45],         // 播放地址解析接口
  "lives":   [1],          // 直播（分组 → 频道 → urls）
  "flags":   [12],         // 播放器 flag 白名单
  "spider":  "https://raw.liucn.cc/box/sub/jar/2212.jar;md5;80DA...",
  "ijk":     [2],
  "ads":     [57]
}
```

单条站源长这样：

```json
{"key":"csp_Kunyu77","name":"🌤雨季三千","type":3,"api":"csp_Kunyu77",
 "searchable":1,"quickSearch":1,"filterable":1}
```

`api` 是 `csp_Kunyu77` 这种**类名**，不是 URL。它指向 `m.json` 里 `spider` 那个 `2212.jar` 中的 Java 类。
这就是"空壳"的含义：壳负责界面和播放，内容逻辑全在这 220 个爬虫类里。

还有一点：这个仓库的活跃度停在 2023-04，README 自己写着
「以上为互联网流传资源，不保证内容的真实性和可靠性」。实测 60 个协议型站源里，
**当下只有 20 个能正常响应**。

### 2. `FongMi/TV` —— 是真的应用，但是安卓

```json
模块: app / catvod / quickjs / nodejs / chaquo / thunder / tvbus / runtime / hook
语言: Java + Kotlin + Gradle
```

关键的是这三个运行器，它们决定了鸿蒙上做不了什么：

| 模块 | 干什么 | 依赖 | 鸿蒙能否复现 |
|---|---|---|---|
| `catvod` | 加载 `2212.jar`，反射调用 `csp_xxx` 类 | `DexClassLoader`（ART 虚拟机） | ✗ 没有 JVM，也没有 DEX 加载器 |
| `quickjs` | 跑 `.js` 爬虫 | 自带 QuickJS 原生库 + `hiker` JS API | △ 理论上可交叉编译 QuickJS 到 OHOS，但 `hiker` 里大量 API 依赖 Java 侧实现 |
| `chaquo` | 跑 Python 爬虫 | Chaquopy（CPython for Android） | ✗ 没有 CPython 运行时 |

所以"把 FongMi 编译成鸿蒙应用"不成立——Gradle 产物是 `.apk`，鸿蒙只装 `.hap`；
即使反编译出 dex，鸿蒙也没有虚拟机去执行它。

## 二、鸿蒙上到底能做什么

幸好 TVBox 协议分两类，其中一类是**纯 HTTP**：

| type | 含义 | 数据来源 | 数量 | 本项目 |
|---|---|---|---|---|
| 0 | XML 采集接口 | `GET ?ac=list` / `?ac=videolist` / `?ac=detail` | 5 | ✅ 完整实现 |
| 1 | JSON 采集接口 | 同上，返回 JSON | 45 | ✅ 完整实现 |
| 4 | 包了一层 `data` 的 JSON | 同上 | 10 | ✅ 拆包后同样处理 |
| 3 | 爬虫（csp_ / jar / js） | Java/JS 运行时 | 220 | ❌ 平台不支持 |
| | | | **280** | **可用 60** |

`parses` 里 45 条解析规则，可用的（type=1、URL 有效）34 条，本项目全部接入。

## 三、协议实现里踩到的三个真实坑

这些都是拿真实站源跑出来的，不是推测。

### 坑 1：CDATA 必须先取内容再清标签

采集接口的片名是这样给的：

```xml
<name><![CDATA[日夜：女人们喜欢的男人]]></name>
```

如果直接 `<[^>]+>` 去标签，`<![CDATA[...]]>` 会被整段当成一个标签删掉，
结果是**所有片名都变空字符串**。列表看着有 20 条，全是没有名字的空白卡片。

正确顺序：先定位 `<![CDATA[` 与 `]]>` 取中间内容，再处理 HTML 实体。

### 坑 2：`?ac=list` 不一定返回分类

标准苹果CMS 的 `?ac=list` 返回 `<class><ty id="1">电影</ty></class>`。
但实测 `ckzy.me` 这个站，`?ac=list` 直接返回**影片列表**，根本没有 `<class>`。

处理方式：拿到 `<video>` 块后，从每条的 `<tid>` + `<type>` 反推分类。

### 坑 3：分类 id 里可能只有两条内容

在 `hongniuzy2.com` 上实测：

```
?ac=list                 → total=116409   ← 全集
?ac=videolist&t=1&pg=1   → total=2        ← 分类 1 只有 2 条
?ac=videolist&t=&pg=1    → total=116409   ← t 传空 = 全集
```

如果默认进第一个分类，用户会看到"只有 2 部片"，以为站源坏了。
所以本项目在所有分类前强制插入一个 **「全部」（t 传空串）** 作为默认入口。

## 五、结论

1. 你给的两个仓库，一个是数据、一个是安卓应用，都**不能直接变成鸿蒙应用**。
2. 鸿蒙能承载的是 TVBox 的**协议层**，不是**爬虫层**。
3. 本项目把协议层完整实现了（含三处真实坑的修正），覆盖 60/280 个站源。
4. 想让那 220 个爬虫站源也能用，唯一路径是：在鸿蒙上用 ArkTS 逐个重写爬虫
   （每个站一条解析规则，工作量按站计）。这属于另一个项目，不适合塞进 v1。
